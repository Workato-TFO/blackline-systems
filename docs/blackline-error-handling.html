Phase 1

Handle errors in a recipe

In this phase, you'll retry failed records, raise Jira issues and send one summary email, then test with a malformed file.

Pattern

Retry, ticket, summarize

Retry a failed record first, create an issue only when the retry fails, and send one summary of all failures, so people see only what retries could not fix.

1.1

Retry and report failed records

The refactored recipe is now filed and named, but it still has no error handling. Management wants a Jira ticket the moment a record fails, and the support team needs one notification listing every failed record.

Overview

You'll add Monitor On Error blocks that retry each failed record within 5 seconds. If the retry fails, the recipe creates a Jira issue, and one email lists every error. Any other error also creates a Jira issue. Every issue summary starts with your name.

Apply these values

RetryAt least once, within 5 seconds

Jira issue summaryStarts with your name
Detailed steps 6 steps

Retry handles temporary failures. A Jira issue captures each record that still fails, and one email gives the support team the whole list at once. A Jira issue for any other error means nothing slips through. Every participant's issues land in one shared Jira project, so your name at the start of each summary lets you find your own.

  • Add Monitor On Error blocks to the CSV-to-Salesforce recipe to catch and manage errors.

  • For each record in the CSV, retry at least once within 5 seconds when an error occurs.

  • If the record still fails after the retry, create an issue in Jira.

  • Notify the support team by email with the list of all errors at once. Use the Email by Workato app and send the email to yourself for testing.

  • For any other error, create an issue in Jira so nothing slips through the cracks.

  • Start the summary of every Jira issue the recipe creates with your name, so you can find your own among the shared issues.

Verify the recipe retries a failed record at least once within 5 seconds before it creates a Jira issue.

1.2

Comment and test the error handling

Jordan has added the handling but has not seen it catch a real failure. Before management relies on it, Jordan wants each step commented for the next reader. Jordan also wants a malformed file run through the recipe, to watch the retry, the tickets and the email happen.

Overview

You'll add a comment to every step and follow the best practices you have learned, including folder structure and naming conventions. Then you'll upload a malformed CSV to test the handling.

Detailed steps 2 steps

Comments make the handling readable for the next developer. A malformed file shows whether the retry, the Jira issues and the email behave as you designed them.

  • Add a comment to every step to describe what is going on. Follow the best practices you have applied so far, such as folder structure and naming conventions.

  • Test the error handling by uploading a malformed CSV. Create your own, or use the example file in File Storage at /Workshop Assets/Lab Files/Error Handling/Customer Loan Data/customer_loan_data_dirty.csv.

Verify uploading the malformed CSV sends one email that lists all of the errors.

Reflect

Now that you've added error handling to a recipe, consider what this means for the support team that receives the alerts.

  • Why does the recipe retry a failed record before it creates a Jira issue, and what would the support team see if it skipped the retry?
  • Why does the support team get one email that lists every error instead of one email per record?
  • Which errors in your recipe would fall under "any other error", and how would you tell them apart from a failed record?

Wrap-up

Jordan's recipe now retries a failed record, opens a Jira issue when the retry fails and sends the support team a single email with every error. Next, Jordan turns to another team's report recipe, which uses more resources than it needs.

  • Monitor On Error with retry. Catch the error at the record level and retry at least once within 5 seconds before treating it as a failure.
  • Ticket per failure, one summary per run. Create a Jira issue for each failed record and send one email that lists all of them.
  • Comments on every step. A comment on each step explains what is going on, so the next developer can read the error path without running it.
